# 面试讲述与学习路线

项目完成范围与个人贡献见 [MY_CHANGES.md](../../MY_CHANGES.md)，实际测试与全局门禁见 [04-verification.md](04-verification.md)。

## 可以怎样介绍

“我先围绕库存数据更新做过重构，后来用个人供应链项目把库存查询、补货参考和人工采购串起来。继续看客服工作，我发现有库存、采购意向已确认、外箱唛完成很容易被误说成已经发货。因此我基于开源 Pi Native CRM 做了一个聚焦的二次开发：用 viewer 身份通过实际 HTTP 读取第二项目的库存、补货参考与表单准备字段，校验来源、SKU 和时间，再经 Pi 工具循环形成待人工复核的草稿。整个 CRM 和它已有的多 Agent 等能力属于上游，我展示的是自己的履约事实核验链路。”

随后说明：本轮 Pi SDK 与工具是真实执行，官方 Faux provider 是脚本化的，没有真实 LLM 请求；演示不自动发送，也不持久化到 CRM。真实 CRM 有可选的服务端事实上下文端口，但没有本轮完整 Supabase 和客户渠道端到端验收。

## 先读哪一部分

1. 看 [来源说明](../../UPSTREAM.md)与[个人贡献](../../MY_CHANGES.md)，区分下载基线、本轮新增和旧功能复核。
2. 看 [业务链路](01-business-flow.md)，解释为什么库存、采购、准备表单与物流是不同事实。
3. 阅读 `lib/ai/fulfillment/evidence.ts` 及测试，手算日期、组织/SKU 一致性，观察什么情况下事实会被隐藏。
4. 阅读 `supply-chain-reader.ts`，从登录到实际查询逐条理解字段白名单、超时、部分成功和失败回执；确认没有采购管理员请求。
5. 阅读 `draft.ts` 和 `lib/agent-runtime/pi/tool-observation-fixture.ts`，沿工具定义、执行、观察到最终草稿，区分 SDK 执行与脚本化 provider。
6. 沿 `generateReplyDraft → preview.operationalEvidence → inbound-turn.buildOpening → operational-opening.ts` 看真实 CRM 可选接线；解释为什么动态事实进入 opening，而非稳定系统指令。
7. 阅读 `native-import.ts`，在 Windows 下理解路径归一化、tsx 与 Node ESM import 的兼容问题；再看 `scripts/portfolio/` 与前端如何构成独立演示。

## 常见追问与回答要点

| 追问 | 应能解释的内容 |
| --- | --- |
| 为什么要做第三个项目？ | 从运营内部决策走到客户沟通，解决“准备事实被误说成履约结果”的具体问题 |
| 为什么不让模型自己判断？ | 可重现规则校验身份范围、对象和时间；本轮用 Faux 演示工具/草稿边界，未测真实模型判断质量 |
| 有库存为什么不能保证发货？ | 快照时效、预留、订单关联、出库和物流属于不同证据，未覆盖的部分继续核实 |
| 采购确认和发货的区别？ | 只确认采购意向，不产生收货或库存变化；当前 HTTP reader 也没有取得采购事实 |
| 表单完成为什么不能证明发货？ | 外箱唛有值只说明准备字段存在，尚缺客户订单关联与出库、承运商证据 |
| 为什么有当天核对和历史回放？ | 源数据固定为 2026-09-03；当天核对拒绝把过期库存当现量，历史回放固定评估日并显示真实 HTTP 取得时间 |
| HTTP 失败怎样处理？ | 保留部分成功及失败回执，显示缺口，不用零值或默认成功补造事实 |
| 什么是真实，什么是模拟？ | 跨项目 HTTP、实际 Pi SDK 和工具循环是真实执行；provider 与草稿语言是受控脚本，没有 LLM 请求 |
| 人工复核会发送或保存吗？ | 只标记内存草稿，30 分钟到期或重启丢失；不发送、不写 CRM，不等同正式审批 |
| 真实 CRM 接好了吗？ | 服务端 optional evidence 已接入草稿预览 opening；默认 undefined 不变。无原 UI 导入、无公共事实注入入口，完整数据库/渠道未新验 |
| Windows 上具体解决什么？ | tsx worker 路径含反斜杠，需归一化检测；Pi 是 ESM-only，边界保留 Node 原生动态 import，避免被转成 require |
| 你做了整个 CRM 吗？ | 没有；保留上游 MIT 与来源，展示本轮差异、设计选择和反例测试。旧恢复修复只复核，不冒领 |

## 简历表述

- 基于开源 Pi Native CRM 二次开发客服履约事实核验场景，通过 viewer 只读 HTTP 接入库存、补货参考和表单准备记录，保留来源及时间口径。
- 实现结构化事实校验与客服草稿，区分现存量、准备状态和发货证据；覆盖对象不匹配、数据过期、部分读取失败等反例，并补充真实 CRM 可选服务端上下文接线。
- 使用实际 Pi SDK 与官方 Faux provider 验证工具执行、观察和草稿生成，构建本地人工复核演示；明确真实模型质量、CRM 持久化与正式发送的未验收范围。

根据投递岗位选择其中能完整解释的内容。需要数字时引用 [验证记录](04-verification.md)中的实际范围，不把定向用例加成全量门禁，也不填没有测量的准确率、并发、成本降低或业务转化指标。
